# 회의록 작성 절차

meetings/의 회의 폴더 전사문을 회의록으로 정리한다.
Claude Code는 `/minutes`로 실행한다. 다른 에이전트는 이 파일을 읽고 그대로 따른다.
아래 `$ARGUMENTS`는 사용자가 덧붙인 말(예 템플릿 이름)이다.
`{협업처}`는 `_config/project.md`의 협업처 이름이다.

회의 폴더 `meetings/YYYY-MM-DD_회의명/` 구조:
- `0_source/` 원본 (녹음, STT 결과, `notes.md`, `slides.pptx`). 이 폴더의 파일은 원본이며 수정 금지.
- `1_extract/` 기계 추출 (Whisper json, `slides.md`).
- `2_transcript/` 전사문 `external.md`·`internal.md`, 에이전트 작업 기록 `transcript_log.md`(1절 확인 요청, 2절 메모 분류표, 3절 불일치·가정. 사용자는 읽지 않음).
- `3_minutes/` 회의록. 종합본·공유본·메일 본문.
- 구간은 `external`(외부 참석자와 함께한 본회의, 공유본 대상)과 `internal`(회의 후 내부 논의, 내부 전용).
- `experiments/`의 파일은 회의록·용어 판단의 근거로 쓰지 않는다.

절차:
0. `_config/me.md`·`_config/project.md`·`_glossary/terms.md`·`_glossary/speakers.md` 중 없는 것이 있으면 멈추고,
   이 레포를 처음 쓰는 PC라서 개인 설정이 없는 것이라고 알린 뒤 세팅 절차(`workflows/setup.md`)를 먼저 진행한다.
1. meetings/ 안의 회의 폴더를 확인한다. 여러 개면 대상을 물어본다.
   - `2_transcript/`의 전사문(`external.md`·`internal.md` 등) 전부와 `transcript_log.md` 전체를 읽는다.
     - 1절 확인 요청 (다시 들을 구간, 화자 확인)
     - 2절 메모 분류표
     - 3절 불일치·가정
     - 1절 해결 열이 채워진 항목은 전사 절차(`/transcript`)에서 사용자가 확인해 전사문에 반영한 것이다. 다시 묻지 않는다.
     - 남은 1·3절 항목 중 해석의 여지가 있는 것만 종합본 해당 위치에 확인 표시로 옮긴다 (아래 종합본 규칙의 확인 표시).
     - 회의 폴더 README.md 비고에 transcript_log.md 형식이 다르다고 적혀 있으면 그 설명을 따른다.
   - `2_transcript/`에 전사문이 없고 `0_source/`에 녹음·STT 원본이 있으면 전사 절차(`/transcript`)를 먼저 실행하자고 안내한다.
   - 회의 폴더 없이 단일 전사문만 받으면 회의 폴더를 만들고 `2_transcript/`에 넣는다.
     본회의면 `external.md`, 회의 후 내부 논의면 `internal.md`. 어느 쪽인지 모르면 물어본다.
2. `_config/project.md`(과제 메모 포함), `_config/me.md`(작성자 이름, 내 메일 틀), `_glossary/terms.md`, `_glossary/speakers.md`를 읽고 교정 기준과 공유본 사용 여부를 파악한다.
3. 전사문을 읽으며 AGENTS.md의 Correction Rules(회의록 단계)대로 정제한다.
4. 종합본 템플릿을 정한다.
   - 사용자가 고르는 것은 종합본 템플릿뿐이다. 지금은 `_minutes-full` 하나.
   - `$ARGUMENTS`에 템플릿 이름이 있으면 그 템플릿을 쓰고, 없으면 종합본 템플릿 목록을 보여 주고 선택받는다.
   - `_minutes-shared`(공유본 생성 결과 양식)와 `_minutes-email`(메일 본문용)는 선택 대상이 아니다.
   - project.md의 공유본이 "사용"이면 종합본과 공유본(메일 본문 "사용"이면 메일 본문도)을 함께 만든다는 것을 처음에 알린다.
     정기 의무가 있으면 함께 알린다.
   - 공유본이 "사용 안 함"이면 종합본만 만든다. 아래 공유본·PDF·메일 본문 단계와 코드 대조 점검은 건너뛴다.
     종합본 1~3절은 같은 양식으로 쓰되 공유 영역 제한(external만 사용 등)은 적용하지 않는다.
   - 협업처가 "없음"이면 2절 제목은 "주요 의견"으로 하고 참석자(교수님·연구원)의 지적·요청·제안을 넣는다. 3.2는 두지 않는다.
   - 머리의 일시는 회의 폴더 README.md, 메모, 사용자 말에서 가져온다. 근거가 없으면 사용자에게 묻는다.
     종료 시각을 모르면 시작 시각에 녹음 길이를 더해 적고, 그것도 모르면 시작 시각만 적는다.
5. 회의록을 `<회의 폴더>/3_minutes/`에 저장한다.
   - 종합본 `YYYY-MM-DD_회의명_종합본.md`
   - 공유본 `YYYY-MM-DD_회의명_공유본.md`  
     `uv run scripts/make_shared.py "<회의 폴더>/3_minutes/YYYY-MM-DD_회의명_종합본.md"`로 생성
   - 생성이 오류로 멈추면 출력된 줄 번호를 보고 종합본을 고친 뒤 다시 생성한다. 공유본을 손으로 고치지 않는다.
     - 문장 중간 `(내부)`: 내부 내용을 네 형식(아래 종합본 규칙) 중 하나로 옮김
     - HTML 주석 `<!--`: 내부 묶음 안이라도 오류. 주석 줄을 지움
     - 1~3절에 남은 확인 표시: 스크립트가 한 번에 보고한 전체 목록을 채팅에 번호를 붙여 보여 주고 멈춘다.
       스크립트는 줄마다 줄 번호, 확인 표시 전체(`[? <구간> MM:SS 사유]`), 표시 앞뒤 문장 일부를 출력한다.
       채팅 목록은 번호, 구간·시각, 해당 문장, 사유로 옮긴다. 사용자는 찾을 필요 없이 이 목록만 판단한다.
       - 사용자가 채팅으로 답하면 에이전트가 종합본에 반영하고 다시 생성
       - 사용자가 종합본을 직접 고쳤다고 하면 다시 생성
       - 공유하지 않을 내용이면 `(내부)` 묶음으로 옮김
   - PDF는 사용자가 요청할 때만 `uv run scripts/make_pdf.py "<회의 폴더>/3_minutes/YYYY-MM-DD_회의명_공유본.md"`로 같은 이름으로 만든다.
     공유본을 다시 생성했으면 PDF도 다시 만든다.
   - Notion용 `YYYY-MM-DD_회의명_종합본_notion.md`는 `uv run scripts/make_notion.py <종합본>`으로 만든다 (커밋 제외).
   - 메일 본문 `YYYY-MM-DD_회의명_메일 본문.md` (`_minutes-email` 템플릿, 아래 메일 본문 규칙)
6. 회의 폴더 `README.md` 계보의 3_minutes 행을 갱신한다.
   - 종합본·공유본·PDF·메일 본문의 생성 여부와 날짜
   - 기존 행과 비고는 지우지 않는다.
   - 발송 완료·Notion 업로드는 사용자가 알려 주면 비고에 날짜와 함께 적는다.
7. 저장 후, 전사문에서 새로 발견한 고유명사/용어 중
   용어사전에 없는 것이 있으면 목록으로 보여주고 등록 여부를 물어본다.

메일 본문 규칙 (`_minutes-email`):
- 확인 요청 목록은 공유본 3.2 {협업처} 확인·제공 항목을 바탕으로 쓴다.
- 받는 사람·참조·제목 머리·호칭은 `_config/project.md`("없음"인 칸은 그 줄이나 말머리를 생략), 첫 줄·인사·자기소개·맺음과 문장 습관은 `_config/me.md` "내 메일 틀"의 말투 규칙을 따른다.
- 공유본을 다시 생성하면 메일 본문의 확인 요청 목록도 다시 맞춘다.
- 사용자가 발송했다고 알려 주면 에이전트가 메일 본문 맨 위에 `> 발송 완료: YYYY-MM-DD` 한 줄을 추가한다.
- 템플릿의 HTML 주석은 메일 본문에 남기지 않는다.

발표 자료 규칙 (`1_extract/slides.md` 또는 `0_source/slides.pptx`가 있을 때):
- 쪽수는 장표에 인쇄된 번호로 쓴다. `slides.md`의 `pN`은 파일 순서이며 인쇄 번호와 다를 수 있다 (표지 무번호면 pN−1).
  인쇄 번호는 slides.md만으로 판정할 수 없으므로 `0_source/slides.pptx`를 확인하거나 사용자에게 묻는다.
- `1_extract/slides.md`를 15페이지씩 나눠 읽는다. 없으면 `workflows/transcript.md` 입력 목록의 발표 자료 항목에 적힌 명령으로 먼저 만든다.
- 발표 내용을 요약하는 대제목·소제목은 자료의 문구를 그대로 쓴다 (띄어쓰기·영문 표기 포함).
  페이지 맨 위 상자 `[1]`이 장 제목, 다음 큰 상자의 첫 줄들이 절·항 제목인 경우가 많다.
- 발표에서 건너뛴 페이지는 제목을 만들지 않는다. 자료에 없는 질의응답 주제는 내용으로 제목을 짓는다.
- 본문은 발화를 기준으로 쓴다. 자료 문구는 제목과 표기 확인에 쓴다.
- 단, 계획·수치·방법처럼 발표자가 준비해 온 내용이 발화와 다르면 자료를 따른다(발표 중 말실수로 본다).
  차이 목록(시각, 발화, 자료 페이지·문구)을 채팅으로 알린다. 전사문은 고치지 않는다.
- 자료 제목이 용어사전 표기와 달라도 제목은 자료 그대로 두고 차이를 채팅으로 알린다.

종합본 1~3절(공유 영역) 작성 규칙:
- 1~3절에서 `(내부)` 묶음을 뺀 나머지가 그대로 공유본이 된다. 아래 규칙은 이 공유 영역에 적용한다.
- external 전사문만 사용한다. internal 전사문 내용은 넣지 않는다.
- transcript_log.md 2절에서 공유본 "포함"으로 판정된 메모만 {협업처} 의견·실행항목에 반영한다.
- 공유 영역에 확인 표시(`[?`로 시작)가 남으면 공유본 생성이 멈춘다. 사용자에게 확인해 확정한다.
- {협업처} 의견·실행항목은 항목마다 external 전사문의 시각·발화 근거를 찾는다.
  근거가 internal 구간이나 메모에만 있으면 넣지 않는다.
- 공유본 생성 후 공유본의 수치·담당자·기한·결정사항을 근거 시각과 함께 채팅에 목록으로 보여 주고
  원음 확인을 요청한다. 근거 시각은 공유본 파일에 넣지 않는다.
- 공유 영역에는 틀린 표현을 남기지 않는다. 기술 서술(정의·단위·수식·알고리즘·모델 구성)의 기준은
  `_config/project.md` 코드 대조의 기준 레포·브랜치다(슬라이드나 발화보다 우선). 공유본 생성 전 하위 에이전트로 코드 대조 점검을 돌린다.
  기준 레포가 "없음"이면 이 점검을 건너뛰고, 기술 서술은 발표 자료와 발화 중 확실한 것만 쓴다.
  - 로컬 위치는 PC마다 다르므로 사용자에게 확인한다.
    - 같은 폴더의 작업 사본(worktree 등)은 기준이 아니다.
  - 읽기 전 `git fetch`로 원격을 갱신하고 `origin/<기준 브랜치>`를 기준으로 삼는다.
  - 읽기는 `git show origin/<기준 브랜치>:<경로>`처럼 커밋을 직접 읽는다. 작업 트리와 브랜치는 바꾸지 않는다.
  - 근거는 코드다. 레포 안의 md 문서(docs/ 등)는 작성 당시 다른 목적으로 만든 것으로 보고 최대한 쓰지 않는다.
    문서에 적힌 버전이 현재 코드 버전과 다르면 반드시 의심하고, 코드와 다르면 문서를 "갱신 대상"으로만 보고한다.
  - 다른 브랜치·아카이브 태그에만 있는 코드는 기준 사실로 쓰지 않는다.
- 회의 중 발화가 코드와 다르면 "틀렸다"고 정정하지 말고, 통상적인 표현으로 맞게 고쳐 쓴다.
  지나치게 엄밀하게 정의하려다 틀릴 바에는 일반적인 표현을 쓴다. 다만 사용자가 엄밀하게 쓰라고 한 항목은 엄밀하게 쓴다.
- {협업처} 의견과 관련 없는 지나가는 발언의 오류(그래프 해석 등)는 공유 영역에 넣지 않는다. 필요하면 `- (내부)` 하위 목록에 둔다.
- 회의 중 약속하지 않은 새 작업은 공유 영역(3.1·3.2)에 넣지 않는다. 3.3 추가 할 일 (내부)에만 둔다.
- 코드로 확인된 사실 보강(정의·단위·적용 여부)은 반영 방향 열에 바로 넣어도 된다.
- 발표 성과는 연구 관점으로 쓴다. 예를 들어 기업이 요구한 조건을 제약으로 넣어 수렴시킨 것은 성과로 서술한다.

종합본(_minutes-full) 규칙:
- Notion에 그대로 올리는 전체 회의록이다. 종합본 = 공유본 + 내부 내용.
- 입력은 2_transcript의 모든 전사문(external·internal), 0_source 메모, 1_extract 슬라이드.
- 머리 한 줄(일시·작성자)과 1~3절은 공유본 양식(`_minutes-shared`)과 글자 형식까지 같게 쓴다.
  의견 표의 의견 칸은 `**소제목**<br>내용` 형식.
- 내부 내용은 다음 네 형식으로만 넣는다. `make_shared.py`가 이 묶음을 통째로 지운다.
  1. 제목 줄에 `(내부)`  
     그 제목부터 같은 단계 또는 더 상위의 다음 제목 직전까지 삭제
  2. 목록 항목이 `- (내부)`로 시작  
     그 항목과 더 깊게 들여쓴 이어지는 줄(연속 줄·하위 항목) 삭제. 빈 줄에서 끝
  3. 표 머리 칸에 `(내부)`  
     그 열 전체 삭제
  4. 표 데이터 행 첫 칸이 `(내부)`로 시작 (첫 열이 #이면 둘째 칸)  
     그 행 삭제
- 문장 중간의 `(내부)`는 쓰지 않는다. 지워지지 않아 공유본 생성이 오류로 멈춘다.
- 종합본에는 HTML 주석을 쓰지 않는다. 템플릿 주석도 직접 쓴 주석도 남으면 공유본 생성이 오류로 멈춘다.
- 위치별 내부 내용
  - 머리 아래 `### 회의 정보 (내부)`: 장소/채널, 참석자, 녹음 구간(external·internal 유무), 회의 목적
  - 1절 항목의 내부 메모: 해당 항목 아래 하위 목록 `  - (내부) …`
  - 2절 의견 표: 4번째 열 `(내부) 메모`. 특이사항만 한 문장, 없으면 비움
  - 3.3 `추가 할 일 (내부)`: 외부에 약속하지 않은 할 일 (장표 수정, 레포 정리, 내부 실험, 3.1 항목의 세부)
  - 4절 `내부 논의 (내부)`: internal 구간 정리. 녹음이 없으면 "해당 구간 없음"
  - 5절 `결정·보류 (내부)`: 5.1 결정사항, 5.2 보류·미결, 5.3 다음 회의. 짧은 목록, 근거 시각은 괄호
- 내부 내용은 internal 구간과 공유 영역에서 뺀 사항(발표 자료 오류, 코드와 다른 발언, 미답변 질의의 코드 기준 답).
- 내부 내용 작성 형식
  - 1절 내부 메모·3.3·4·5절도 공유본처럼 `- **소제목**` + 줄 끝 공백 2개 + 2칸 들여쓴 본문 1~3문장
  - 소제목만 보고 주제를 떠올릴 수 있게 짓기. 시간순 메모 나열 금지, 주제별로 묶기
  - 짧은 항목 여러 개는 한 소제목 아래 한 문단으로 합치기. 한 줄짜리 불릿 연속 금지
  - 1절 내부 메모와 2절 메모 열은 특이사항만 한 문장
    (사실과 다른 발언의 정확한 사실, 발표 자료 오류, 미답변 질의의 코드 기준 답, 후속 조치 필요 사항)
  - 특이사항이 없으면 1절은 내부 메모를 두지 않고 2절 메모 칸은 비움
  - 발언 순서 재현, 같은 말 반복, 메타 설명은 삭제. 결정·보류·할 일·사실 정정은 보존
- GitHub 이슈·PR 번호와 "이슈 후보" 표기는 종합본 어디에도 쓰지 않는다.
- 3절에는 표·담당·기한 열을 쓰지 않는다. 담당·기한은 회의에서 언급된 경우에만 항목 끝 괄호로 적는다.
- Notion에는 `uv run scripts/make_notion.py <종합본>` 결과(`_종합본_notion.md`, 커밋 제외)를 붙인다.
  - Notion은 md 표 칸 안 줄바꿈을 지원하지 않아, 2절 의견 표는 목록(번호·소제목 줄 + 본문, 반영 방향·(내부) 메모 하위 항목)으로 바뀐다. 다른 표는 `<br>`만 공백으로 바뀐다.
  - Notion용 파일은 직접 고치지 않는다. 고칠 것은 종합본에서 고친다.
  - 종합본을 고친 뒤에는 Notion용 파일을 바로 다시 생성하고, 사용자가 붙이기 직전에도 다시 생성해 최신본을 보장한다.
- 회의 중 답이 없거나 불완전했던 질의는 관련 1절 항목의 `- (내부)` 하위 목록에 질의와 코드 기준 사실을 함께 적는다.
  관련 항목이 없으면 5.2 보류·미결에 둔다.
- 회의록 내용에 영향을 주는 전사 확인 사항은 전사 절차 마지막 단계에서 채팅으로 처리된다.
  사용자는 `transcript_log.md`와 전사문을 읽지 않고, 회의록 단계에서는 종합본의 확인 표시만 처리한다.
  - 전사 단계에서 처리된 것(전사문에서 표시가 지워진 것, transcript_log.md 1절 해결 열이 채워진 것)은 다시 묻지 않는다.
  - 대상: 전사문에 남은 `[?? MM:SS]` 중 해석의 여지가 있어 회의록 내용이 달라질 수 있는 것, 회의록 단계의 확신 낮은 교정
  - 회의록 내용에 영향이 없거나 맥락으로 한 가지로 정해지는 표시는 옮기지 않는다
  - 형식: 해당 문장 바로 옆에 `[? 구간 시각 사유]` (예 `[? external 12:30 차종명]`, `[? internal 1:02:15]`)
  - 전사문의 `[?? MM:SS]`를 옮길 때 `[? <구간> MM:SS 사유]`로 바꾼다. 구간은 전사문 파일 이름
  - 구간과 시각은 녹음에서 바로 찾을 수 있게 반드시 적는다. 사유는 짧게, 생략 가능
  - 내부 묶음 안에서는 남겨도 되고, 공유 영역에 남으면 공유본 생성이 멈춘다
- 사용자가 요청하면 코드 작업을 연구 코드 레포에 이슈로 등록한다. 그 레포의 기존 이슈 제목·본문 형식을 따른다.
  회의 내용과 어긋나는 기존 이슈를 발견하면 사용자에게 알린다.

사용 예 (Claude Code. 다른 에이전트는 "회의록 만들어 줘"):
- /minutes                → 대화형으로 진행
- /minutes minutes-full   → 종합본 템플릿 `_templates/_minutes-full.md`로 바로 처리 (인자는 앞의 `_`를 뺀 템플릿 이름)
